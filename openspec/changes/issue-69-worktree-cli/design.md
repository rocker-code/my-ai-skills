# Design

## Context

Ver `proposal.md`. `scripts/worktree-reservation` chama `worktree_registry.identity()` sobre o caminho recebido e opera sob lock no Git common dir; parser hoje exige `--path` para todo subcomando salvo `list`, e imprime JSON indentado por padrão. `scripts/install-global` publica snapshots imutáveis em `versions/<SHA>` e alterna `active`, além de gerenciar links de skills. Testes offline existem em `tests/test_worktree_reservation.py` e `tests/test_global_install.py`; `scripts/workflow-status` já agrega GitHub e não deve ser refeito.

## Goals / Non-Goals

**Goals:** interface curta para trabalho no checkout corrente, launcher global com origem e rollback verificáveis, saída resumida que não masque o código do helper; invariantes existentes de owner, lock, drift, fingerprint e JSON intactos.

**Non-Goals:** sessão inferida, alteração de schema do registry ou semântica de `status`, dashboard Git/OpenSpec, instalação real nesta sessão, nova dependência, remoção de checks; consumidores externos aguardam entrega. Não refazer a migração de bootstrap global ou skills de planejamento/Apply/arquivo para OpenSpec 2.0 entregue pela #71; integrar o contrato entregue sem enfraquecer os testes.

## Decisions

1. **Resolver checkout antes de `identity`/lock**: se `--path` estiver ausente num comando que aceita checkout existente, usar `git --no-optional-locks rev-parse --show-toplevel` com `GIT_OPTIONAL_LOCKS=0` no cwd; canonizar caminho e executar a validação de identidade/anchor existente, sem consultar registry para escolher caminho. `reserve --planned`, `cancel-planned`, `mark-removed` continuam exigindo `--path` e `--repository` conforme operação; `list` mantém `--repository`. Se não houver worktree, falhar antes de abrir registry, com caminho para corrigir. Alternativa descartada: `Path.cwd()` (seleciona subdiretório) ou primeira reserva ativa (confunde repos e impersona owner). Para `reserve` de checkout existente, exigir as opções originais de issue/branch/owner e manter recusa de primary.
2. **Separar transporte e apresentação**: centralizar renderização de respostas sem alterar `response()`/`execute()` nem códigos de `ReservationError`. Saída padrão em texto sem cor, com owner completo, estado, HEAD/digest completos, drift e caminhos/conflictos pertinentes; falha inclui ação segura específica por código e condição. O formato textual de `reconcile` expõe `inventory.digest` completo e dados de revisão para takeover, distinguindo-o do digest do checkout; `clean-generated` lista caminho exato, elegibilidade e motivo por candidato; `list` apresenta entradas com caminho, issue, branch, estado e dono, ou lista vazia legível. O `verify` não imprime inventário completo em sucesso. `--json` imprime um único objeto na stdout; stderr não recebe diagnóstico adicional. Aridade/validação de argumentos devem conservar código 2; quando `--json` foi solicitado, planejar o mesmo envelope JSON para erros de uso, sem traceback, mantendo chaves/tipos dos erros operacionais existentes. Não reduzir identificadores para prefixos; formatador nunca converte erro em sucesso.
3. **Launcher gerenciado estável, executa script ativo no diretório correto**: instalador usa diretório de executáveis do usuário (por padrão `~/.local/bin`), confirma descobrimento no PATH efetivo e ausência de comando homônimo de outra origem na resolução. Instala launcher próprio com `exec` para `<data>/active/scripts/worktree-reservation` e encaminha argumentos com aspas (`"$@"`), em vez de symlink isolado do arquivo Python, para que `worktree_registry.py` esteja importável. Antes de publicar, verificar bytes/modo/propriedade do launcher existente via registro gerenciado, sem presumir posse pelo nome; colisões bloqueiam. Integrar criação/rollback à mesma seção protegida por lock do instalador e só publicar depois de validar snapshot; rollback não destrói arquivos preexistentes nem troca active antes de prontidão. Repetição e atualização validam o launcher e preservam mesmo comando apontado a active. Se PATH não incluir o destino, falha explícita ou estado não instalado (não declarar sucesso com comando invisível). Alternativa descartada: modificar shell profile, sobrescrever PATH/colisões, symlink para script Python, executar `install-global` nesta issue.
4. **Uma fonte de exemplos**: atualizar `protocol/WORKTREES.md`, regenerar as cópias oficiais de referências com `scripts/sync-skill-references`, orientação gerada por `guidance()` e exemplos de skills/READMEs relevantes, distinguindo uso global e fallback por caminho absoluto para ambientes ainda não atualizados. Não substituir pipelines de status GitHub/OpenSpec por `verify`; evitar pipe que esconda o exit code do produtor. A orientação gerada deve preservar o contrato de primeiro uso nativo 2.0 entregue pela #71 em `5e33688d2a9db702e6bd0f2027d778f3baebdf35` (skills oficiais, não comandos legados obrigatórios). A #69 acrescenta somente orientação da reserva e testes do launcher, sem reinstalar 1.x, inventar `/opsx-*` ou suprimir provas de descoberta nativa.
5. **Integração protegida após #71**: antes de qualquer integração, verificar posse da reserva e registrar HEAD, status, diff e digest dos 16 arquivos Apply sem stage; preservar os bytes em cópia/patch verificável fora do checkout, sem tratar snapshot como autorização para descarte. Confirmar a revisão exata do merge #71 e sua ascendência; atualizar uma base isolada limpa a partir de `5e33688d2a9db702e6bd0f2027d778f3baebdf35` (ou descendente verificado), nunca fazer merge/rebase/reset/stash neste checkout sujo. Reaplicar as alterações da #69 de forma revisada, arquivo a arquivo, com conferência de diff e digest frente à captura; resolver os seis overlaps (`CHANGELOG.md`, ambos READMEs, `scripts/install-global`, `tests/test_global_install.py`, `tests/test_install_launcher.py`) preservando simultaneamente o launcher #69 e o contrato/testes nativos #71. Conferir os dez arquivos restantes, inclusive referências geradas, e não copiar versões antigas sobre a base nova. Se não houver proteção verificável ou integração sem perda, parar e pedir decisão explícita; não marcar tarefas de implementação apenas com a revisão do plano.
6. **Fronteira auditada do novo candidato e gate**: a [decisão expressa #69](https://github.com/rocker-code/my-ai-skills/issues/69#issuecomment-6931773160) permite novo registro de validação somente após integração protegida em base isolada e revisão independente do candidato. Vincular no novo registro o histórico `/tmp/opencode/issue-69-validation.md` como **INVALID `E_RETRY_LIMIT`**, sem editar nem alterar seu veredito; registrar HEAD limpo, provenance/diff entre candidatos antigo e novo, mudança real do contrato/testes #71, observação factual da assinatura e justificativa da fronteira material de G1. Mudar só nome de arquivo, alvo ou comando não basta. Conferir readiness do novo handoff antes de qualquer G1. Registrar tentativas e diagnosticar falhas equivalentes entre segunda e terceira tentativas, respeitando limite e bloqueios do protocolo; executar gate focado e suíte final exigida no HEAD limpo, com evidências e revisão independente.

## Risks / Trade-offs

- **PATH colide, não inclui diretório ou tem override anterior** → checar resolução efetiva e propriedade antes de qualquer publicação, explicar como reconciliar sem sobrescrever; testes com HOME/PATH descartáveis, inclusive instalação anterior.
- **Falha parcial entre criar launcher e alterar active** → registrar quais arquivos próprios foram criados, rollback simétrico; fault injection já disponível (`MY_AI_SKILLS_FAIL_AT`), adicionar estágio específico e validar old active funcional.
- **Resumo omite dado operacional e induz takeover/limpeza por adivinhação** → testes por comando com `inventory.digest` versus digest do checkout, candidatos elegíveis/recusados e lista vazia/múltipla; manter parâmetros, recibos e códigos de falha invariantes.
- **`--json` em erro de parse** → erro de uso ocorre antes do `try` atual; isolar serialização sem alterar validação/exit code; garantir stdout somente JSON nos erros declarados e códigos 2/3/4/5/6/7.
- **Git dentro de subdiretório ou repo nested** → `--show-toplevel` retorna a worktree que realmente contém cwd; `--path` explícito prevalece, identity revalida common dir/remote. Não autorizar caminhos de destino ausente por fallback.
- **Diferença entre pacote active instalado e checkout da issue** → não executar instalação real; validação de instalador em HOME temporário, preservar estado global real.
- **Checkout antigo e gate bloqueado** → o worktree #69 ainda tem testes 1.17.0 e orientação `/opsx-*`, enquanto a revisão #71 entregue usa skills nativas OpenSpec 2.0. A terceira falha G1 de mesma assinatura precedeu o diagnóstico em `/tmp/opencode/issue-69-validation.md`: `E_RETRY_LIMIT` histórico continua INVALID após a #71. Não relabelar, apagar histórico, repetir G1 neste candidato ou remover assertions para simular sucesso. A autorização expressa para **novo registro auditado** não dispensa revisão independente da fronteira e da assinatura factual após integração; se a mudança não for material, manter o bloqueio e escalar, sem reset. Não rodar init/update local ou global nesta etapa.

## Migration Plan

Após integração protegida da revisão #71 e das alterações sujas #69, implementação e testes autorizados, instalação/atualização global explicitamente solicitada entrega o launcher na mesma transação da revisão ativa. Antes disso documentação pode usar fallback absoluto; consumidores M2T/Rancho só mudam após contrato entregue. Em falha de atualização, manter instalação e launcher anteriores sem migração implícita de personalizações. O merge #71 não autoriza automaticamente atualização da instalação global, do projeto ou retry do gate G1 bloqueado. A decisão posterior permite somente novo registro para candidato realmente novo, com vínculo ao histórico inválido e handoff pronto antes dos testes; na etapa Apply, arquivar/sincronizar os três deltas apenas após testes focados/finais no HEAD limpo, revisão independente do gate e validação estrita conforme workflow.
