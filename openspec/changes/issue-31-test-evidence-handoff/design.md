# Design — issue-31-test-evidence-handoff

## Context

Ver proposal.md (Why). Estado observado em `main @ 5825a9c`:

- `scripts/workflow-event` L113-115 aceita `--evidence` só como `https://github.com/...` ou SHA; grava strings em `event.evidence` e `record.evidence`.
- `scripts/workflow_metrics.py` `parse_run_comment` exige `schema_version == 1`; `summarize_run` repassa `evidence`; `scripts/workflow-report` L208-209 concatena as strings.
- `skills/prepare-pr/SKILL.md` (seção "Pre-PR self-review", parágrafo "Run permitted validations…"), `skills/apply-issue/SKILL.md` ("Before commit…"), `skills/pr-audit/SKILL.md` L26 e `skills/post-pr-audit/SKILL.md` L12 descrevem em prosa prova do código exato e reuso restrito, sem mecanismo.
- `protocol/TEST_STRATEGY.md` define a matriz Scenario | Critério/risco | Camada | Teste; `scripts/sync-plugin` empacota-o em 8 skills e copia helpers para `plugins/my-ai-skills/scripts/`.
- Sem CI hospedado (`.github/` ausente). Gate local: `python3 -m unittest discover -s tests`.
- Helpers existentes usam só stdlib + `git`/`gh` por subprocess; testes usam `gh` falso em `PATH` e diretórios temporários.

## Goals / Non-Goals

**Goals:**
- Registro genérico e verificação completos para comandos não M2T (inclui comandos M2T executados como comando comum).
- Transporte entre worktrees/sessões do mesmo clone sem passo manual; entre runtimes via pacote portátil ou metadados publicados.
- Registro estável e referenciável por `evidence:<evidence_id>` (#32 correlaciona execuções pelo seu próprio `execution {kind,id}`; #34 referencia a prova pelo `evidence:<id>` e pelo ID de obrigação), sem que irmãs alterem o manifesto.
- Reusar o estado canônico do checkout de #35 (`scripts/worktree_registry.py`) em vez de definir outro fingerprint.

**Non-Goals:**
- Adaptador/leitura do registro nativo M2T (follow-up bloqueado por M2T #12 — ver "Contract handoff").
- Decidir suficiência de cobertura (continua em TEST_STRATEGY) ou selecionar testes por impacto (#33).
- Estado ao vivo de processos/jobs, reconciliação de execução ativa (#32).
- Reserva de escrita de checkout (#35); log de hipóteses de retry (#34).
- Upload de logs para serviços externos (gist, artifacts) — não implementado; apenas referência por URL+checksum quando o projeto já os tiver.

## Decisions

### D1. Helper novo `scripts/workflow-evidence` + biblioteca `scripts/workflow_evidence.py`
Segue o padrão `workflow-event` + `workflow_metrics.py` (CLI fino, lógica importável e testável). A biblioteca importa `code_state(checkout, *, exclude_paths=(), include_ignored=())`, `drift_report(baseline, current, *, checkout)`, `FINGERPRINT_VERSION` e `is_known_generated` de `scripts/worktree_registry.py`, conforme o contrato aprovado de #35 em `75b8740`; não redefine o estado canônico. `CodeState` contém `head`, `digest` (`sha256:v1:<hex>`), `entries` com `path`/`status`/`sha256`/`deleted`/**`index`** (blob, modo e stage) e `generated`; expõe `load_manifest/verify_manifest`. O CLI define `sys.dont_write_bytecode = True` antes de importar módulos irmãos (R6). `worktree_registry.py` passa a ser companheiro obrigatório de `workflow-evidence`. **Dependência rígida: #35 implementado, validado e mergeado antes do Apply de #31**; conferir API real após merge, sem editar código da #35 nesta mudança.
Alternativa rejeitada: estender `workflow-event` — mistura registro de tempo (single-writer orquestrador, GitHub) com prova local do implementador e aumentaria conflito com #32.

Subcomandos: `record` (executa `-- <cmd...>`), `register-hosted` (resultado de CI: URL, SHA, status; sem log), `verify`, `export`, `import`, `publish`, `list`, `show`, `prune`. `record` gera o `evidence_id`, cria o diretório do registro com `status: running` e emite `{"evidence_id": …}` como primeira linha em stderr **antes** de executar o comando (R3: o orquestrador pode usar `observe --execution-kind test_run --execution-id <evidence_id>` em #32). Saída `--format text|json`; exit codes: `record` propaga o do comando; `verify` retorna 0 somente se todas as execuções pedidas estiverem `verified` e `passed` **e cada gate pedido estiver vinculado à obrigação e satisfeito**, 3 para não verificado/gate pendente, 2 para erro de uso. Uma execução hosted verificada sem vínculo pode aparecer no JSON com estado `verified`, mas a checagem do gate retorna 3.

`register-hosted` aceita URL/run_id de um run GitHub Actions no repositório declarado; consulta somente leitura à API GitHub via `gh` (autenticada, testada com `gh` falso) para obter `head_sha`, conclusão, `created_at`/`updated_at` e estado terminal, sem tomar status/head digitados como prova. `verify` consulta novamente a origem para confirmar run_id, repo, head e conclusão; indisponibilidade de API, fonte não suportada ou resultado não terminal → `metadata_only`/`incomplete` e gate pendente, não `verified`. Para hosted, `exit_code` é derivado (`0` para sucesso, `1` para falha terminal; **não** é alegação de exit code original do comando do CI), `counts.source: none` salvo relatório acessível, `artifacts: []` quando não há log; a confirmação externa prova a **execução**, não qual obrigação ela cobre. Para satisfazer um gate hosted, obter do ramo-base confiável uma política vigente que vincule o ID da obrigação a um workflow path e check/job name obrigatório; consultar jobs/check-runs da API para provar que esse check específico pertence ao run_id e passou no SHA exato. A política vem da configuração protegida do repositório/branch-base (branch protection ou ruleset efetivo e mapa de obrigações versionado na base), nunca do manifesto importado, comentário ou branch do PR. Se não há mapeamento confiável ou a API não permite confirmar a identidade do check, o gate fica pendente (`not_applicable`), mesmo se a execução genérica foi `verified`. Este repositório não configura CI hospedado; nenhum gate hosted é inferido aqui. Esse caminho não enfraquece as obrigações locais nem faz chamadas de CI pagas.

### D2. Manifesto `my-ai-skills.test-evidence/v1`
Campos (obrigatórios em negrito): **`schema`**, **`evidence_id`** (`ev-<UTC>-<8 hex>`, mesmo padrão de `new-run-id`), **`kind`** (`local`|`hosted`), **`repository`** (owner/repo do `origin`, se houver, e toplevel relativo não publicado), **`code`** {**`head`**, **`fingerprint`**, `registry_digest` (`sha256:v1:…` de #35), `dirty`, `changed_paths` [{path, status, sha256|deleted, index}], `config_paths` [{path, sha256|missing}], `excluded_paths` [declarados], `fingerprint_after`}, **`command`** {argv mascarado, cwd relativo ao toplevel}, **`selection`** (string livre: filtro/caminhos), **`obligations`** [{**`id`** (mesmo ID da linha da matriz; é o que #34 referencia), `required_gate`: `local`|`hosted`|null, `relevant_paths`: [glob]}], `openspec_change`, **`runner`** {python, os, hostname-hash, ferramentas declaradas via `--tool name=version`, nomes de env permitidos, identificadores não secretos via `--env-id NAME=ID`, `compatibility_digest`}, **`started_at`**, **`finished_at`**, **`exit_code`** (null se interrompido), **`status`** (`running`|`passed`|`failed`|`interrupted`), `counts` {tests, failures, errors, skipped, source: `junit`|`declared`|`none`}, **`artifacts`** [{name, role: `log`|`report`, sha256, bytes, state: `present`|`missing`}], `hosted` {url, run_id (= id `ci_run` de #32), head, clean: bool} (kind hosted), `correlation` {run_id, issue_url, stage, worker_id} (opcional; definido e mantido por esta mudança — #32 não o altera), `producer` (**provisório e não validado**: null ou ausente nesta versão — ver D9), `extensions` {} (genérico, namespaced, preservado; nada atribuído nesta mudança). `obligations` no manifesto são alegações do produtor; para gate hosted o vínculo normativo vem apenas da política confiável do ramo-base e da identidade do check confirmada na API, não desses campos.
Leitores ignoram e preservam chaves desconhecidas; mudança incompatível exige `v2`.

### D3. Fingerprint (camada sobre #35)
Base: `code_state(checkout, exclude_paths=saídas_declaradas, include_ignored=configs_declaradas)` de #35 — `head`, digest versionado e entradas por caminho incluindo índice; gerados conhecidos classificados por `is_known_generated` ficam fora do digest. `exclude_paths` recebe globs relativos das saídas declaradas (`--report`, `--artifact`, `--output-dir`); `include_ignored` recebe caminhos/globs relativos das configurações ignoradas declaradas, além das configurações rastreadas já incluídas pelo Git. Camada de evidência: `sha256` sobre JSON canônico de {`FINGERPRINT_VERSION`, `CodeState.digest`, lista ordenada de (`--config PATH`, `sha256|missing`)} — o hash explícito detecta também desaparecimento de configuração e é deliberadamente redundante quando #35 já a incluiu. Configuração declarada não pode ser excluída como saída. Persistir os dois `CodeState.to_json()` (ou suas entradas equivalentes) para comparar paths em outro runtime. Capturado antes e depois de `record` com as mesmas exclusões; divergência → `status_note: concurrent_change` e verificação `ambiguous`. Saídas declaradas e gerados conhecidos **nunca** causam `ambiguous` por si. Custo proporcional ao diff.
Comparação no `verify`: recalcula a camada no candidato com as exclusões/configurações do registro; se igual → corresponde. Se diferente, usar `drift_report(baseline, current, checkout=…)` de #35 para HEAD e entradas completas (inclusive `index`) e unir com configs cujo hash explícito diferir. Não comparar somente hash do arquivo da working tree: blob/modo/stage no índice podem mudar sem mudança no conteúdo atual.
Compatibilidade do ambiente (separada de `code_state`, sem mudar a API de #35): o registro local captura `sys.version_info` (major/minor), plataforma/arquitetura e os pares ordenados declarados `--tool NAME=VERSION` e `--env-id NAME=ID`; `compatibility_digest` é SHA-256 do JSON canônico desses itens. `ID` é um identificador de perfil/toolchain **declarado não secreto**, não o valor de uma variável de ambiente nem o hash de um segredo; `NAME` segue `^[A-Za-z][A-Za-z0-9_.-]{0,63}$`, `ID`/`VERSION` seguem `^[A-Za-z0-9][A-Za-z0-9_.:+/-]{0,127}$`, e entradas com aparência de credencial são recusadas. `--env-name` anota somente nomes permitidos, sem leitura de valores; se fornecido no registro local, requer `--env-id` para cada nome declarado (senão recusar `record`), pois nomes sozinhos não provam compatibilidade. `verify` mede novamente Python/plataforma e exige os mesmos identificadores via `--tool`/`--env-id` quando foram declarados; ausentes → `incomplete` (recuperação: fornecer identificadores não secretos ou rerun), divergentes → `stale` com `environment_changed` e obrigação afetada, mesmo se HEAD/diff coincidirem. O operador seleciona as dimensões relevantes e confirma que os IDs correspondem ao ambiente real; identificadores autodeclarados não são atestado criptográfico, mas o verificador **nunca** aprova ignorando uma dimensão declarada. Nenhum valor de env, hash de valor secreto, hostname cru ou identificador de ambiente/toolchain entra na projeção GitHub.
Alternativas rejeitadas: fingerprint próprio (duplicaria #35, ruling R1); `git stash create` (escreve objetos e não cobre configs ignoradas).

### D4. Armazenamento e transporte
- Local: `$(git rev-parse --git-common-dir)/ai-workflow/evidence/<evidence_id>/{manifest.json,artifacts/…}` (namespace `ai-workflow/` de WORKTREES.md, também usado por #35), comum a todas as worktrees do clone (T1 mesmo host). Nunca dentro da árvore de trabalho; nada é commitado.
- Outro runtime: `export` gera `<evidence_id>.tar.gz` (manifesto + artefatos + `SHA256SUMS`); `import` valida membros (sem caminhos absolutos, `..` ou links) e checksums antes de gravar no armazenamento local. O orquestrador transporta o pacote pelo meio já autorizado do runtime (cópia para a sessão seguinte); o helper não envia logs a terceiros.
- GitHub: `publish --issue|--pr URL` grava **projeção** `my-ai-skills.test-evidence-public/v1`, nunca o manifesto, num comentário oculto `<!-- my-ai-skills-test-evidence:v1 -->` por `evidence_id` (atualiza se existir, como `workflow-event`). Allowlist construída de zero: `schema` público, `evidence_id` validado, `kind` enum, `repository` estritamente `owner/repo`, `code.head` SHA hexadecimal, `status` enum e, somente para hosted, `hosted.run_id` decimal e `hosted.url` canônica `https://github.com/<owner>/<repo>/actions/runs/<run_id>` sem query/fragment/userinfo, coerente com repo/id. Recusar publicação se qualquer campo incluído for inválido; descartar **todas** as demais chaves (inclusive desconhecidas), `selection`, `command`, `obligations`/paths, `runner`, configs/fingerprints/digests, `extensions`, `producer`, `correlation`, mensagens e artefatos — não serializar objeto inteiro, não publicar hashes de valores secretos. Limite: projeção > 60 000 bytes rejeitada. `verify --from-github URL` lê/valida o schema público e nunca o trata como manifesto completo: para local sem pacote/artefatos → `metadata_only`; para hosted confirma na API GitHub repo, run_id, HEAD e conclusão terminal na hora de verificar e exige candidato limpo no SHA exato → `verified`/`passed|failed` para a **execução** sem log local; API indisponível/não confiável → `metadata_only` e não PASS. A projeção não inclui obrigação: para satisfazer gate hosted exige política de checks do ramo-base efetiva, mapa confiável obrigação→workflow/check e job/check-run correspondente confirmado na API; manifesto importado ou comentário nunca cria esse vínculo. Sem os três, execução pode estar `verified`, mas a obrigação fica pendente. Escopo de escrita idêntico ao já usado por `workflow-event`.
Alternativas rejeitadas: refs Git customizadas no `origin` (efeito remoto novo, retenção difícil); gist (exposição por URL); commit no branch (polui PR).

### D5. Conteúdo sensível
Logs e relatórios ficam apenas locais/no pacote. argv mascarado para `--*token*|--*password*|--*secret*|--*key*=valor`, `Authorization: …`, `ghp_…`/`github_pat_…`, `://user:pass@`. Ambiente: somente nomes de uma lista permitida (`CI`, `PYTHON*`, `NODE_ENV`, …) e `--env-name` explícito, nunca valores; IDs declarados em D3 não derivam de valores secretos. `hostname` armazenado como hash. Publicação usa apenas a allowlist de D4, não um mascaramento superficial do manifesto. Documentação proíbe passar segredos em argv/IDs; `export` exibe aviso de que logs/manifestações locais podem conter dados sensíveis e exige revisão antes de compartilhar fora do repositório.

### D6. Estados de verificação (ordem de precedência)
1. Entrada ilegível/campos obrigatórios ausentes/schema desconhecido → `incomplete`; `--from-github` valida o schema **público**, não exige campos do manifesto privado ausentes por design. Qualquer campo incluído inválido → `incomplete`.
2. Para manifesto local, `fingerprint != fingerprint_after` → `ambiguous`; projeção pública não contém fingerprints e nunca os inventa.
3. `status: running|interrupted` ou exit code null no manifesto local → `incomplete` (uma execução ainda em curso nunca passa); projeção hosted obtém o resultado terminal/exit code derivado da API, não do comentário.
4. Gate `required_gate: local` atendido por registro `kind: hosted` → `not_applicable` (AC5; hospedado nunca satisfaz gate local). Gate `hosted` com registro `kind: local` → `not_applicable`.
5. Registro `kind: local` com fingerprint ≠ candidato **ou** ambiente declarado incompatível → `stale` com `changed_paths` e/ou `environment_changed` e impacto por obrigação (`affected`/`unaffected`; incompatibilidade ambiental sempre `affected`); dados de compatibilidade declarados mas não fornecidos na verificação → `incomplete`, nunca ignorados. Obrigação com `required_gate` (qualquer tipo) é sempre `affected`. Registro `kind: hosted` com `hosted.head` ≠ SHA do candidato, candidato com `CodeState.entries` não vazio, ou `hosted.clean` falso → `stale`; com `head` = SHA do candidato limpo → segue para 6/7 (pode ser `verified` como execução). Cabe à API comprovar URL/run_id/head/status; declaração no manifesto não basta. Para satisfazer gate `hosted`, exigir **também** política efetiva do ramo-base com workflow/check mapeado à obrigação e job/check-run daquele run confirmado na API como concluído com sucesso nesse SHA. Run bem-sucedido de outro workflow/check no mesmo SHA, mapeamento só no manifesto, política ausente/inacessível ou job inconcluso deixam o gate pendente (`not_applicable`), mesmo que a execução genérica seja `verified`.
6. Artefato local `missing` ou ausente/checksum divergente → `incomplete` (se veio da projeção GitHub sem artefatos locais → `metadata_only`). Para hosted, que não contém log local por design, a confirmação da execução hospedada na origem substitui a exigência de log local; sem confirmação da origem é `metadata_only`. A projeção não vincula obrigações: estado `verified` da execução hospedada não dispensa prova independente de vínculo ao gate.
7. Caso contrário → `verified`, com `result` = `passed` se `exit_code == 0`, senão `failed` (hosted: derivado da conclusão confirmada na API; prova verificada de falha; só `verified` + `passed` **e vínculo à obrigação** satisfaz gate).
Cada estado inclui `reasons[]` e `recovery` {obligations, action: `rerun`|`import_bundle`|`restore_artifact`|`provide_identifiers`}; gate hospedado sem vínculo exige conferir política/mapeamento de checks do ramo-base e identidade do job na API, nunca importar um manifesto autodeclarado como substituto.

### D7. Invalidação por obrigação (T4)
`relevant_paths` declarados por obrigação no `record` (`--obligation T2:scripts/**,tests/test_x.py`). Interseção com caminhos divergentes → `affected`. Sem declaração → `affected` (conservador). Um registro local divergente continua `stale` como um todo, inclusive quando uma obrigação é classificada `unaffected` (informativo, **não** `verified`); a decisão de reuso continua das regras de `pr-audit`/`post-pr-audit` (nunca reutilizar através de mudanças de runtime/build/dependência/teste relevantes) e o gate final obrigatório sempre roda no candidato final. Se mudança de HEAD não puder ser atribuída com segurança a paths, classificar `affected`.

### D8. Integração ao workflow (prosa)
- TEST_STRATEGY: coluna `Evidence` na matriz (`evidence_id` + estado); nova seção "Evidence handoff" **depois de "Review and stop"** (R9) com estados, transporte, retenção, sensível e precedência de gates `local|hosted`.
- `templates/pull-request.md` (seção Validation): uma linha por obrigação `PASS|FAIL|NOT RUN: <obligation> — evidence:<id> (<verify state>)`; #34 acrescenta depois o bloco opcional `attempt-log`.
- apply-issue (parágrafo "Before commit…", R9): registrar execuções focais e uma suíte preliminar durante Apply; o gate **final** deve ser reexecutado via `workflow-evidence record` somente após archive/sync + mudanças de prepare-pr + commit (D8), exportar/publicar conforme o runtime, listar IDs no handoff. A posse do checkout e o `verify`/`checkpoint` de #35 continuam obrigatórios para comandos com efeitos; a prova não substitui reserva de escrita.
- prepare-pr / pr-audit / post-pr-audit: `workflow-evidence verify` no candidato; reportar estado por obrigação; `metadata_only`/`incomplete`/`ambiguous`/`not_applicable` = não verificado; reexecutar apenas obrigações em `recovery`.
- Freeze do candidato: Apply executa testes focais durante implementação, arquiva/sincroniza OpenSpec e valida. Prepare-pr conclui self-review, distribuição/gerados, template e demais mudanças; **commita tudo antes** do gate local final. Com o HEAD final e checkout limpo, executar a suíte final via `record` e verificar `verified` + `passed` com `code.head == git rev-parse HEAD` e fingerprint idêntico; guardar `evidence_id` fora do commit (handoff/comentário/PR) para não criar ciclo. Push/criação/edição de metadados da PR não mudam HEAD; qualquer commit posterior (incluindo correção de revisão, arquivo ou template) invalida o gate final, que deve ser reexecutado e registrado no novo HEAD limpo antes de alegar PASS. Publicar/transportar a prova após o freeze; revisão exige correspondência do SHA exato, nunca só de paths supostamente não afetados.
- address-pr-review: após correção, verificar e reexecutar só o afetado.
- milestone-orchestrator (seção "Durable handoff", R9): transportar `evidence_id`/pacote no handoff do worker; `workflow-event --evidence evidence:<id>`.
- update-ai-workflow: incluir `workflow_evidence.py` e `worktree_registry.py` como companheiros obrigatórios de `workflow-evidence`.
- Quando o helper não estiver instalado, manter o comportamento atual em prosa e marcar a prova como não verificada pelo helper (sem bloquear projetos que não o instalaram).

### D9. Fronteira M2T (contract-handoff design-review)
O registro M2T (#12) ainda não existe nem tem schema congelado. Esta mudança não lê nem mapeia campos M2T. `producer` é **provisório e não validado**: a forma sugerida `{name, schema, record_ref, digest}` é só um marcador para o adaptador futuro e pode mudar após `CONTRACT FROZEN`; nesta versão MUST ser null ou ausente, e o helper não o valida nem o interpreta. O follow-up (adaptador M2T + teste de contrato) fica CONTRACT_BLOCKED em M2T #12. Requisitos do consumidor que o produtor precisa cobrir (insumo para M2T #12, não contrato):

| Cenário do consumidor | Operação/campos necessários do produtor | Estado/erro | Ponto de validação | Evidência / lacuna |
|---|---|---|---|---|
| Ligar execução ao código testado | ID de execução, repositório, HEAD, fingerprint incl. alterações locais | ambíguo se mudou durante a execução | captura no host M2T | GAP — M2T #12 aberto, sem PR (`m2t@eb40523`) |
| Distinguir sucesso/falha/interrupção/desconhecido | fase, estado terminal verificado, exit code original, horários | incompleto/desconhecido explícito | reconciliação do runner | GAP |
| Verificar relatórios | lista de artefatos com presença e checksum, exportação portátil | ausente explícito | exportação M2T | GAP |
| Consultar de outro runtime | consulta estruturada versionada por ID / pacote exportado | schema desconhecido → rejeitar | leitura pelo consumidor | GAP |

Resultado: `CONTRACT GAP — integração nativa M2T` (apenas esse cenário). Caminho genérico não depende do produtor: `CONTRACT DESIGN READY` não se aplica porque não há contrato a consumir nesta mudança.

### D10. Retrocompatibilidade de métricas
Esta mudança é dona da allowlist de `--evidence` (R4): URL `https://github.com/…`, SHA, ou `EVIDENCE_REF_PATTERN = ^evidence:ev-[0-9]{8}T[0-9]{6}Z-[0-9a-f]{8}$` (constante nomeada em `workflow-event`); qualquer outro valor é rejeitado. #32 pode mover os validadores para `workflow_metrics.py` mantendo a semântica; `test_event_accepts_evidence_reference_and_rejects_path` guarda a regra, e o esquema tipado de `--log-ref` (#32) não amplia `--evidence`. A linha `sys.dont_write_bytecode = True` de #35 em `workflow-event` é preservada. Nada mais muda em `workflow_metrics.py`/`workflow-report` (strings continuam strings, `schema_version` continua 1).

## Matriz requisito → código → teste (TEST_STRATEGY)

| ID | Critério de aceite / risco | Código | Camada | Teste (novo/existente) |
|---|---|---|---|---|
| T1 | AC1: outra sessão/diretório verifica sem repetir teste | armazenamento comum, `export`/`import`, `verify` | Fixture helper (Git temporário + `git worktree add`; segundo clone) | novo `test_record_verified_from_other_worktree`, `test_bundle_import_in_other_clone` |

## Risks / Trade-offs

- [Outro runtime sem acesso ao diretório Git comum nem pacote] → execução local `metadata_only`, recuperação = importar pacote ou reexecutar a obrigação; hosted pode ser `verified` após consulta confiável à API, mas gate exige vínculo independente à obrigação.
- [Custo de hash em diffs grandes] → só caminhos alterados e configs declaradas; sem cópia da árvore.
- [Mascaramento incompleto de segredos] → logs nunca publicados; projeção pública de campos fechados sem strings livres/valores/hashes de env, argv mascarado só no manifesto local; documentação proíbe segredos em argv/IDs.
- [Identificadores de ambiente/toolchain autodeclarados incorretos] → comparação explícita detecta drift declarado, não atesta verdade dos IDs; executor escolhe e confirma perfil não secreto relevante, ausência na verificação não vira aprovação.
- [Commit após gate final] → HEAD muda mesmo quando só o arquivo OpenSpec/PR muda; gate local final roda depois de archive + prepare-pr + commit, reexecutado a cada novo HEAD.
- [`unaffected` usado para pular reexecução indevida] → informativo; obrigações com `required_gate` sempre `affected`; regras de reuso de `pr-audit`/`post-pr-audit` prevalecem.
- [Conflito com #32 em `workflow-event`] → só a constante `EVIDENCE_REF_PATTERN` e a validação; #32 rebaseia e mantém a semântica (R4).
- [Conflito com #33 em `TEST_STRATEGY.md`] → coluna da matriz + seção própria "Evidence handoff"; #33 altera seções de planejamento/retomada.
- [Bifurcação por #34] → #34 mantém o raciocínio de retry só no bloco `attempt-log` e referencia a prova por `evidence:<id>` + ID de obrigação; não lê nem grava o manifesto (R2).
- [API de #35 diferente da aprovada em `75b8740`] → dependência rígida em #35 mergeado; confirmar `code_state`/`drift_report`/`FINGERPRINT_VERSION`/`is_known_generated` e entradas do índice no código real; se não forem entregues, parar e revisar o plano (não reimplementar o fingerprint).
- [Saídas não declaradas dentro da árvore] → continuam podendo gerar `ambiguous` (conservador); documentação orienta declarar `--report/--artifact/--output-dir`.
