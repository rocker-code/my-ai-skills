# Worktree lifecycle

## Inventory and ownership

Before planning, Apply, PR corrections or cleanup, verify the repository remote, run `git worktree list --porcelain`, and inspect branch, HEAD, `git status --short --untracked-files=all` and linked PR for each relevant checkout. Resolve the Git common directory with `git rev-parse --path-format=absolute --git-common-dir`; worktrees share refs and administrative state. Do not treat a missing path as permission to recreate or prune it.

Use one branch/worktree per issue across planning, Apply and PR corrections. A fresh session is a context boundary, not a reason to create another checkout. Reuse the existing verified issue worktree and proposal commit. If several candidates exist, reconcile their branches, unique commits, diffs and PRs before choosing; preserve every candidate until ownership is clear. Never change another worker's branch or move its files.

Keep the primary checkout for coordination. Respect the repository's configured worktree location; otherwise use a sibling directory `<repository>-worktrees/issue-<number>-<slug>`, outside the source tree. Use a verified remote base for a new branch and record its SHA. Do not repoint an existing issue branch to the newest base. Refresh remote refs when online; report stale/offline evidence explicitly.

The coordinator serializes inventory → reservation → creation and grants only one active writer per issue worktree. Maintain a local registry in the Git common directory (`ai-workflow/worktrees.json`), outside tracked source, containing repository identity, issue URL, branch, absolute path, base SHA, proposal SHA, PR URL/head, owner session/run, lifecycle state, test sandbox and last verified timestamp. Update atomically. Across coordinators, use a repository-common exclusive lock with an available locking mechanism; if exclusivity cannot be established, do not dispatch a concurrent writer. Do not steal a lock or release a reservation based only on age: establish that the prior session stopped. The registry is local coordination data, never proof of GitHub delivery or a validation gate.

Lifecycle: `RESERVED` → `ACTIVE` → `WAITING` / `HANDOFF` → `RETAINED` / `CLEANUP_ELIGIBLE` → `REMOVED`. Reconcile registry entries with actual Git and live GitHub state on resume. An absent registry is a reason to reconstruct ownership, not to duplicate or delete existing worktrees. Block only an ambiguous/conflicting issue.

### Reservation helper

The global installation provides `worktree-reservation` on PATH. In any subdirectory of an existing checkout, use `worktree-reservation verify --session <worker-id>` (or `--path <checkout>` to select another checkout explicitly, including a path with spaces). Its default native summary shows result, state, owner, full HEAD/digest and drift; failures give a safe next action. `reconcile` shows the full `inventory.digest` required for takeover, `clean-generated` shows exact candidates and eligibility, and `list` shows every reservation. Use `--json` for automation, without a formatting pipe that masks exit status. Before global installation, call `${XDG_DATA_HOME:-$HOME/.local/share}/my-ai-skills/active/scripts/worktree-reservation` by absolute path with `--path`. The caller must always provide its own `--session` for owner-gated commands, never infer it from a recorded owner.

When installed, `scripts/worktree-reservation` coordinates cooperative writers in `<git-common-dir>/ai-workflow/worktrees.json` (schema 1, atomic replacement under a common `fcntl` lock; lock failure is closed). Use `reserve --planned --path <new-path> --repository <existing-checkout> --issue <URL> --branch <branch> --session <worker-id> --run <run-id>` before `git worktree add`, then repeat `reserve` without `--planned` on the created checkout to activate. The helper never creates/removes a worktree. If add fails, `cancel-planned --path <new-path> --repository <existing-checkout> --session <same-id> --run <same-id> --reason <text>` is permitted only while the destination is absent, unregistered in Git and still owned by that session/run; partial creation requires manual inspection. Existing checkouts without a complete entry enter `RECOVERY_REQUIRED`, **not** a free state. Review `reconcile --path <checkout> --json`'s real Git inventory and digest, establish external stopped-writer evidence, then use `reconcile --takeover --expected-owner <id|unknown> --stopped-evidence <reference> --inventory-digest <digest> --session <new-id> --run <run-id>`; the helper rechecks the inventory and refuses a registered live same-host owner PID. Age, missing PID and a textual evidence reference alone never prove a writer stopped. Explicit `--owner-pid` is for a long-lived worker, not the ephemeral CLI process. No direct reservation or drift acceptance bypasses recovery.

Before writes, tests with effects, commits or pushes, the owner calls `verify --path <checkout> --session <id>`; after its own writes, `checkpoint --path <checkout> --session <id>` records the new baseline, then `verify` again before the next mutation. `release --state WAITING|RETAINED|CLEANUP_ELIGIBLE` and `handoff --from-session <id> --to-session <id> --run <run-id>` require the current state to match the checkpoint; coordinate handoff only **after** the prior worker returns. Released, ownerless entries are compared to their baseline on `reserve`: external HEAD, index or working-tree changes stop with drift (exit 4); only `reserve --accept-external --reason <text>` or the current owner's `reconcile --accept-external --session <id> --reason <text>` records acceptance. Checkpoint cannot erase previously detected drift. `mark-removed --repository <existing-checkout>` records removal only after Git's inventory no longer lists the checkout; it does not clean files. `status` and `list` only report state. `--session` and `--run` use `SAFE_ID` (ASCII alphanumeric first, then up to 99 alphanumeric/`._:-` characters). `--json` on reserve/status/verify and conflicts includes stable `ok`, `exit_code`, `error`, `path`, `issue_url`, `branch`, `state`, `owner`, `head`, `digest`, `drift`, `generated_paths`, `unknown_untracked_paths`, `last_verified_at`; drift reports HEADs, commits, committed paths, changed paths, divergence and detection time. Exit codes: 0 success, 2 usage, 3 owner/recovery conflict, 4 drift, 5 lock unavailable, 6 identity mismatch and 7 corrupt registry. Main checkout needs explicit `--allow-primary` where project policy permits.

The public `worktree_registry.py` API (`FINGERPRINT_VERSION`, `SAFE_ID`, `KNOWN_GENERATED_PATTERNS`, `is_known_generated`, `code_state(checkout, *, exclude_paths=(), include_ignored=())`, `drift_report(baseline, current, *, checkout)`, `IndexEntry`, `PathEntry`, `CodeState.to_json()`) defines the versioned `sha256:v1:` code fingerprint of HEAD, path statuses/content and staged index blobs/modes/stages. Known bytecode paths are inventoried separately from the digest; `include_ignored` opts named ignored configuration into it. Git filenames that are not valid UTF-8 use Python's `surrogateescape` round-trip: canonical fingerprint bytes preserve the original filename bytes, while registry/CLI JSON escapes the surrogate characters for safe transport. Renaming or changing canonical calculations requires a new fingerprint version. Read-only Git inspections disable optional index locks.

`track-generated --path <checkout> --session <id> -- <command>` is **opt-in**. It requires a verified owner, snapshots safe regular unstaged bytecode before and after a successful cooperative command with no known child still running, then checkpoints its effects and publishes only *new* magic-valid `*.py[co]` with full hash, `lstat` metadata, session/run and opaque execution reference in the common-dir registry (at most 256 per checkout). It never stores arguments, environment or output. Failed commands, pending children or failed snapshots do not authorize cleanup; they may still leave effects requiring inspection. Verify again after the wrapper's checkpoint. `clean-generated` lists eligible and refused candidates; `clean-generated --apply --session <id> --paths <exact-relative-path> --reason <text>` rechecks ownership, identity, receipt, drift, safe ancestors, magic, full hash, metadata and no-follow file handle under the lock. Unknown/manual/preexisting bytecode, including valid magic without matching provenance, remains list-only. Never sweep ignored roots such as `.venv/`, remove an unknown file or remove a nonempty directory. `PYTHONDONTWRITEBYTECODE=1 python3 -m unittest discover -s tests` avoids incidental test bytecode; installed Python helpers disable their own bytecode writes.

This coordinates participants that use the helper; it cannot prevent a non-cooperating writer from changing HEAD/files between inspections or at the final unlink boundary. Changes in the verify→checkpoint interval are attributed operationally to the owner, not proven authored by it. Even opt-in before/after snapshots cannot prove that an outside writer did not create a candidate during the observation window, nor detect children that escape process-group supervision. Recovery evidence text is not authenticated by the helper. Pause on uncertainty rather than treating a local registry as proof of ownership, delivery or safety.

## Session handoff and environments

Record issue, path, branch, HEAD, clean/dirty state, owner, pinned proposal revision, PR, last verified gate and next action. End the planning writer before starting the fresh Apply writer on that same checkout. Transfer ownership explicitly. Reviewers can read immutable commits; serialize operations that mutate a checkout, index, generated files or test environment. Stop the writer or use an isolated review checkout if review tools write files; register any temporary review checkout and subject it to the same cleanup rules.

Before commands that write, commit, test or push, verify working directory, repository, branch, HEAD and reservation. Run commands with an explicit working directory. Stage exact paths only. Do not copy uncommitted files between worktrees, stash somebody else's changes, force checkout/reset, or create a replacement branch to bypass a dirty checkout. Preserve partial work and report the precise recovery action when ownership cannot be established.

A worktree does not isolate Docker mounts, databases, ports, caches or Magento generated files. Record the actual mounted source and sandbox for each test worker. Allocate isolated disposable resources or serialize shared resources; never silently test another checkout. Follow repository setup commands and keep secrets/generated assets out of commits.

### M2T sandbox during work

For a project using M2T, keep its integration and GraphQL sandbox selections with the **issue worktree**, not the lifetime of a command, Apply worker or session. On first use, record the canonical checkout path, each known selection (`integration` or `graphql` plus its exact `sandbox-id`), execution/run ID or receipt, relevant private-log reference and ownership evidence in the existing issue handoff/worktree inventory. Record additional GraphQL tokens as they are created; `worktree-reservation --set sandbox` can identify one selection but is not a multi-instance ownership ledger. Do not add a parallel registry. On transfer to a new worker, reconcile that handoff with the current checkout reservation, `m2t status` and the worker's execution evidence before reusing a selection. A listed instance, a matching name, an M2T lock or a run ID alone does not establish workflow ownership or that a test passed. Checkout writer reservation and M2T's execution lock protect different resources.

Use the public `m2t test`/`m2t graphql` interface to prepare or reuse the selected sandbox. M2T decides installation, cache and baseline validity; the workflow still checks test evidence against the current code/selection and reruns affected obligations after relevant changes. Never impose `down`, `reset`, manual Docker preparation or an unsafe skip at the end of a test, commit, Apply, handoff, pause or session. Diagnose an unhealthy sandbox before an explicit recovery reset. Keep the checkout, owned selections and handoff on PR-open, failed, blocked, interrupted or uncertain work. A disappearing process, container state or last log line is not a completion callback: check actual worker/test liveness before transferring ownership or closing out.

Consume bounded M2T summaries, exit codes and execution IDs by default. For `test`/`graphql`, reconcile a recorded run when needed with `m2t runs show <run-id> --json`; its private host log is under `${XDG_STATE_HOME:-$HOME/.local/state}/m2t/runs/<run-id>/output.log`, but a successful summary does **not** promise a log path. `unit`/`exec` return separate execution receipts and private logs under `m2t/executions`, not `m2t runs` records. On failure, inspect only the relevant private log excerpt without copying secrets into a public issue/PR; neither a status listing, receipt, log file nor run ID substitutes for a verified test result on the current candidate. M2T continues to clean its own disposable `unit`/`exec` copies and volumes; retention here applies to integration/GraphQL instances and preserves shared vendor/Composer caches.

## Automatic housekeeping

Worktree cleanup is a required workflow closeout action, not an optional suggestion to the owner. After each verified issue delivery, automatically inspect and remove eligible managed worktrees before scheduling more work. Do not create a separate worktree for every phase or retry. Reuse the same issue checkout through proposal, Apply, fixes and final review whenever exclusive access is possible.

At every orchestrator startup/resume and at run end, reconcile worktrees previously created by this workflow in the selected repository. Remove eligible leftovers from prior runs, including completed issues outside the currently selected milestone, only when durable registry/handoff evidence establishes workflow ownership and all safe-closeout conditions below pass. This housekeeping does not authorize implementing or merging outside the selected scope. Unknown/user-created checkouts stay untouched. Do not ask the owner to approve routine removal of verified eligible managed worktrees. An open PR or an unfinished issue remains retained. If GitHub or local ownership cannot be verified, retain it and report the blocker; continue cleaning other eligible worktrees.

Finish with a compact inventory table: issue, branch/path, PR/delivery, action (`reused`, `removed`, `retained`) and reason. List any residual managed worktree and its exact pending condition, including removal refused by Git. A successful delivery report must disclose incomplete housekeeping instead of silently abandoning directories.

## Safe closeout

In manual merge mode, retain the issue worktree and branch at `READY_TO_MERGE`. Retain blocked, failed and interrupted work with its recovery handoff. An open PR, old timestamp or green CI never makes a checkout disposable.

After verified merge, release the worker. Kaizen is on demand and does not block cleanup. Mark cleanup eligible only after confirming: the PR's delivered scope and head match this issue; no active owner, tests or shell depends on the directory; tracked, untracked and ignored files contain no work/data to preserve; no unique unpushed or undelivered commits remain; and proposal/validation/handoff evidence is durable. Inspect ignored files as well as ordinary status. For squash/rebase merges, establish delivery from the merged PR and its exact reviewed head; lack of ancestry alone does not mean work is undelivered. Any uncertainty means retain with a reason.

For M2T-backed worktrees, close out **before** Git removes the checkout: reconcile the durable handoff's exact owned selections with `m2t status` and actual liveness, retaining unknown or externally owned instances untouched. From outside the checkout, pass its still-existing path explicitly to the public interface: `m2t --worktree <checkout-path> down` for a proved integration selection; `m2t --worktree <checkout-path> down --scope graphql --sandbox-id <exact-owned-token>` separately for **each** proved GraphQL selection. Never infer further tokens from the default, a name prefix or age. If using `--no-wait`, exit 73 means the instance lock is busy, not successful cleanup. Record each selection's exit/result and do not loop on failure; a partial down, missing ownership evidence, active owner/test/process, busy lock or uncertain selection retains the worktree and its handoff reference for diagnosis/retry. Do not use global `gc`, blanket Docker removal or cleanup of shared vendor/Composer caches or another worktree's resources. Down destroys exclusive instance volumes (including tmpfs database state); it is not a way to preserve that data. Only after all known owned selections are safely resolved and the existing Git eligibility checks still hold may non-forced worktree removal proceed.

Remove an eligible checkout only with non-forced `git worktree remove <verified-path>` from another directory. If Git refuses, retain and explain; never retry with `--force`, `rm -rf`, forced branch deletion or blanket `git clean`. Branch deletion is optional and follows repository policy; use `git branch -d` only when Git considers it merged, otherwise retain it (including squash-merged branches). Do not prune other worktree records or delete remote branches as a side effect. Mark registry removal only after verifying Git's worktree list. Report created, reused, retained and removed worktrees with reasons.

For M2T work, include a compact per-issue result for each known selection: checkout, scope/token (only where safe to disclose), `removed` or `retained`, reason/exit code and next action. Do not report total closeout when any selection or the checkout remains unresolved. Retain open PRs and manual-merge work without running down.
